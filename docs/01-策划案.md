| 语法 | 命中的文件数 | 优先级 |
| --- | --- | --- |
| 代码块 ` ``` ` | **163**（67%） | **P0，最高** |
| 表格 `\|…\|` | **106**（43%） | **P0**（这也印证了表格确实重要） |
| 图片 `![]()` | **72 篇**（引用点 737 处） | **P0** |
| Mermaid | **19** | P1（懒加载） |

| 数学公式 `$$` | 2 | P2（接入 KaTeX 即可，成本低） |
| 任务列表 / 脚注 | 1 / 1 | P2 |
| `==高亮==` | **0（真用到）** | 见下方说明，**P3 可砍** |

> **结论**：这个库是**技术笔记库**——代码块和表格占绝对主导，公式几乎不用。所以工作量的分配应该是「代码块 + 表格 + 图片」远重于「公式 + Mermaid」。这与通用笔记软件的优先级不同，是为你的库定制的。

**⚠️ `==高亮==` 的实测陷阱（值得单独写，因为它是个"看起来有其实没有"的坑）：**

粗扫全库，`==...==` 命中 45 处、分布在 8 个文件里——看着像"高亮用得很频繁"。但逐行核对**代码块外**的命中，只剩 3 处，全是**误报**：

```
GHLog.cpp.md      == DLDU_Bit || DataUnit ==          ← C++ 比较运算符
运算符.md         | == | 检查两个操作数的值是否相等 |   ← 表格里的运算符说明
校长模拟器.md      id == "ChildUIEscReturn" and ...    ← Lua 代码漏了围栏
```

**真·高亮语法用量 = 0。** 这直接决定了三件事：

1. `mark` 相关的主题规则（`dyzj` 给 `==...==` 写了很显眼的黄底）**优先级降到 P3**，不做也不影响观感。
2. **如果做了行内 `==高亮==`，绝对不能碰代码块和行内代码内部**——否则 `GHLog.cpp.md` 里 32 处 `==` 会被高亮成一片黄色，那是纯粹的视觉灾难。
3. 同理，`<br>` 只有 5 篇、`<details>` / `<video>` / `<kbd>` / `alt="blink"` 等自定义容器**实测 0 处**——全都可以安心砍掉。

### 1.4 顺带发现的一件事

你库里有一份 `总合笔记软件策划案.md`（2026-09-11），开篇写着：

> 「**不重写编辑器**。你已有 Typora + Obsidian，日常写作不改；「总合笔记」是架在文件系统之上的聚合与索引层。」

那份方案选择了"只读聚合层"，明确回避了编辑器内核。

现在的需求变成了**"做一个能穿 Typora 主题的编辑器"**，等于把当初标注为"工作量翻 3 倍"的那条路正面走了。这不冲突——上次是解决"笔记太散"，这次是解决"主题不同步 + 想玩"——但要意识到：**这次的活比上次重 3 倍，且没有 deadline**。玩票项目无所谓重，只是别低估。

## 4. 为什么是 Electron（而不是 Tauri / 网页版）

| 方案 | 主题保真度 | 文件读写 | 结论 |
| --- | --- | --- | --- |
| **Electron** | 内置 Chromium，**所有机器渲染一致**；Typora 本身也是 Chromium 系，CSS 行为最接近 | Node `fs` 直接读写，简单 | **选它** |
| Tauri | 用系统 WebView（WebView2 / WKWebView），CSS 行为随系统版本漂移；主题这种"像素级"需求最怕这个 | 需要 Rust 侧写命令 | 不选 |
| 浏览器版 | Chromium 一致，但需每次授权目录、没有原生菜单、不像"应用" | File System Access API | 你要求桌面端，不选 |

对**主题兼容**这个目标来说，"渲染引擎一致"比"安装包小 60MB"重要得多。这是选 Electron 的唯一决定性理由。

## 5. 技术核心：Typora 主题怎么才能真的"穿上"

这一章是整个项目的技术难点，也是"玩"的价值所在。

### 5.1 问题的本质

Typora 主题是一份**普通 CSS**，但它写死针对 Typora 的 DOM：

```css
:root { --bg-color: #fff; --text-color: #333; --monospace: "JetBrains Mono"; }
#write { max-width: 860px; font-family: "Source Han Serif SC"; }
#write h1 { font-size: 2em; border-bottom: 1px solid #eaecef; }
#write p { line-height: 1.8; }
#write blockquote { border-left: 4px solid #dfe2e5; color: #777; }
.md-fences { background: #f6f8fa; border-radius: 6px; }
#write table td, #write table th { border: 1px solid #dfe2e5; padding: 6px 12px; }
```

而我的编辑器如果把正文渲染成 CodeMirror 的 `.cm-line`，那么 `#write h1` 这条规则**根本匹配不到任何元素**——主题加载了，等于没加载。

> 这是所有"兼容 Typora 主题"的尝试失败的原因：不是 CSS 难解析，是 **DOM 对不上**。

### 5.2 解决策略：DOM 契约 + 选择器映射（双管齐下）

**A. 尽量让 DOM 长得像 Typora**（能直接匹配的部分，一点不改）

- 编辑器整体挂在 `<div id="write">` 里 → 所有 `#write ...` 后代选择器天然生效。
- 富元素用真实标签 + Typora 的类名：
  - 代码块 → `<pre class="md-fences"><code class="language-ts">`
  - 表格 → 真实 `<table><thead><tr><th>`（Typora 表格也是真 `table`）
  - 图片 → 真实 `<img>`
  - 公式 → `<span class="md-math">` + KaTeX
- 于是 `#write table td`、`.md-fences`、`#write img` 这些规则**原样生效，不需要翻译**。

**B. 对行级块做选择器映射**（对不上的部分，翻译一下）

CodeMirror 的一行必须是 `.cm-line`，不可能变成 `<h1>`。所以给每一行打上语义 class，再把主题规则"改名"：

| Typora 选择器 | 我方选择器 | 说明 |
| --- | --- | --- |
| `content` | `.jd-content` | **Typora 私有元素**，`dyzj` 用它画右下角背景图（§5.2-E，实测必需） |
| `#write h1` … `#write h6` | `#write .jd-h1` … `.jd-h6` | 行级 class，CM6 `Decoration.line` 挂载 |
| `#write h1 span` | `#write .jd-h1 span` | 标题文字要包一层 `<span>`，否则悬停横线不出现 |
| `#write p` | `#write .jd-p` | 每个段落行 |
| `#write blockquote` | `#write .jd-quote` | 引用行（含嵌套 `jd-quote-2`） |
| `#write ul` / `ol` | `#write .jd-list` | 列表整体容器感 |
| `#write li` | `#write .jd-li` | 列表项行 |
| `#write hr` | `#write .jd-hr` | 分隔线 |
| `.md-fences` | `pre.jd-code` | 代码块外层（保持 `pre` 语义，组合选择器才有东西可匹配） |
| `.md-fences .CodeMirror` | `.jd-code-inner` | 代码块内部（语法着色我们自己做） |
| `.md-fences .CodeMirror-code > *` | `.jd-code-line` | 代码块每一行（悬停高亮靠它） |
| `.CodeMirror-activeline` | `.jd-code-active-line` | 光标所在代码行 |
| `.md-task-list-item > input` | `.jd-task input` | 任务列表复选框 |
| `#typora-source` | `#jd-source` | 源码模式容器 |
| `#write .md-meta` | `#write .jd-meta` | 语法标记（`#`、`**`、`` ` ``） |
| `.md-toc-inner` `.md-math` `.footnotes` | `.jd-toc-inner` `.jd-math` `.jd-footnotes` | 目录/公式/脚注容器 |

映射表是一份**可编辑的 JSON**（`src/theme/mapping.json`），不在代码里写死——发现哪个主题长得不对，加一条映射就行，这是长期可维护的关键。

**C. 主题自带的基础样式要补齐**

许多 Typora 主题只写"差异部分"，默认排版依赖 Typora 内置基础样式。所以我们内置一份 `base.css`（等价于 Typora 默认主题的排版骨架：正文行高、标题间距、列表缩进、代码块内距、表格边框），**先加载 base，再加载主题**，让"只写了一半"的主题也能看。

**D. `@import` 必须递归展开**（实测踩到的坑，不展开等于没装主题）

`dyzj-dark.css` 全文只有 60 行，真正的样式全在别处：

```css
@import url(./source/dyzj.css);        /* 36KB / 1607 行 —— 真正的主题 */
@import url(./source/darkcode.css);    /* 代码高亮的 token 配色 */
/* 而 source/dyzj.css 自己还有两层： */
@import './dy/iconfont.min.css';       /* 引用块图标用的 iconfont */
@import './zj/fonts.css';              /* JetBrains Mono + Source Sans Pro，23 个 @font-face */
```

→ **一共 4 层、5 个文件、内联后约 1989 行、319 条规则**。只读主 css 的话，拿到的是那 60 行变量声明，主题形同没装。

所以管线第一步必须是**递归内联 `@import`**，且**每层的相对 URL 以该文件所在目录为基准解析**（`source/zj/fonts.css` 里的 `url('JetBrainsMono-Regular.woff2')` 要落到 `themes/source/zj/`，而不是 `themes/`）。

> **这一条不实测发现不了。主题长得不对，八成是 `@import` 没展开，而不是选择器映射写错了。**

**E. `content` 元素：Typora 的私有标签，必须提供等价容器**

`dyzj` 有三条规则挂在 `content` 上（去掉注释后实测确认，不是标准 HTML 标签，是 Typora 自己的 `<content>` 元素）：

```css
body:not(.typora-sourceview-on) content {
    background: var(--bgimg-url) no-repeat;     /* 右下角那张 12% 的背景图 */
    background-size: 12%; background-position: 86% 100%;
}
content #md-searchpanel { background: var(--bg-color); }
```

两条 `content` 规则就是**右下角背景图 + 页面底色**。所以我们的 DOM 必须有一个真实存在的 `content` 容器，而且**必须是 `#write` 的父级，不能是同一个元素**：

```html
<body>
  <div class="jd-content">        <!-- ← 对应 Typora 的 <content>，管整页底色和右下角背景图 -->
    <div id="write">              <!-- ← 管正文列，max-width:860px; margin:0 auto -->
      …
    </div>
  </div>
</body>
```

为什么必须分开：`content` 要的是**整页**背景（`background-position: 86% 100%`，即视口右下角），而 `#write` 是 `max-width:860px; margin:0 auto` 的窄栏。合成一个元素的话，那张背景图会被塞进 860px 的正文列里、跑到正文框的右下角 —— 位置完全错。`content #md-searchpanel` 这条规则也印证了 `content` 是**外层**容器（搜索面板不在 `#write` 里）。

> 用 `<div class="jd-content">` 而不是字面的 `<content>`：后者是 HTML 规范里已废弃的标签名，虽然 Chromium 照样渲染，但没必要为一个名字踩语义坑。映射表里 `content → .jd-content` 一条搞定。

> 顺带说：这个主题自己有个 bug —— `--bgimg-url: url(./bg-dark.gif)` 会解析到 `themes/bg-dark.gif`，而文件实际在 `themes/source/bg-dark.gif`。**Typora 里这张图本来就没显示出来**。我们的管线要不要"顺手修好这个 bug"？决定：**不修，原样复刻**——目标是"和 Typora 一样"，不是"比 Typora 好看"。修了反而变成两套观感。这条写进规则：**翻译过程不修正主题的 bug**。

**F. 级联顺序不能乱**（`@import` 的副作用，实测才看得见）

`@import` 在 CSS 规范里必须写在文件最前面，这带来一个反直觉的结果：**主文件里写在 `@import` 之后的规则，反而会覆盖被 import 进来的样式**。`dyzj-dark.css` 结尾就是两段：

```css
#write { max-width: 80em; }      /* ← 覆盖掉 source/dyzj.css 里的 860px */
img { filter: brightness(80%); }  /* ← 裸标签选择器，所有图片整体压暗 20% */
```

两件事都必须照做：

1. **内联时保持原文件的规则顺序**，不能按"先 @import 后主文件"重排——重排的话 `#write` 会退回 860px 窄栏，整页行宽全错。
2. `img { filter: brightness(80%) }` 是**裸标签选择器**，我们的 `<img>` 也会被压暗。这是对的（Typora 里就是这效果），**不要为了"图片更好看"去给它加例外**。同理还有 `h1`~`h6`、`table`、`blockquote` 那一批裸标签规则，全部照翻。

> 提示：`max-width: 80em` 意味着这个主题是**宽栏**（约 1280px），不是 860px 窄栏。所以 §0 里"行宽 780px"的内置兜底主题和它在观感上完全不同——这也正常，兜底主题只是"没有 Typora 主题时别太丑"，不追求一致。

### 5.3 适配管线（数据流）

```
%APPDATA%\Typora\themes\*.css           ← 零拷贝，直接读，不复制
        │
        ├─ 1. 列出主题（文件名 + 可选预览图）
        │
        ├─ 2. 递归内联 @import（上限 8 层，检测环形引用）
        │      ├─ 每层的相对 url() 以「该文件所在目录」为基准重写为 file:///
        │      │   · 剥掉 ?t=1670129411561 这类缓存串（file:// 下会 404）
        │      │   · local() 字体名、data: URI 原样保留
        │      │   · 解析不到的文件 → 进 report，不静默
        │      └─ **保持规则原有顺序**（主文件里 @import 之后的规则要能覆盖被导入的样式，见 §5.2-F）
        │
        ├─ 3. postcss 解析 → 逐条规则改写选择器（§5.2 映射表）
        │      ├─ 命中映射 → 改名后保留
        │      ├─ 含 #write / body / html / :root → 原样保留
        │      ├─ 应用外壳专属（#typora-sidebar 等）→ 丢弃并记录
        │      ├─ @font-face / @keyframes → 全保留
        │      └─ .cm-s-inner / .CodeMirror 作用域类 → 剥掉后保留（token 配色要用）
        │
        ├─ 4. 产出三样东西
        │      ├─ css：改写后的样式表
        │      ├─ report：{ 应用 N 条 / 丢弃 M 条 / 丢弃明细 / 缺字体清单 }
        │      └─ vars：:root 变量表（侧栏、状态栏跟着变，整体观感统一）
        │
        └─ 5. 注入 <style id="typora-theme"> → 热重载（监听文件变化，400ms 防抖）
```

**关键取舍**：宁可"翻译得不完美"，也不要"复制一份改好的 CSS 到项目里"。因为用户（我）随时会换主题、改主题，**运行时翻译 + 热重载**才能做到"Typora 里改一行，这里刷新就变"。

### 5.3.1 实测：把 `dyzj-dark.css` 真跑一遍这条管线

| 分类 | 条数 | 说明 |
| --- | ---: | --- |
| 含 `#write` / `html` / `body` / `:root` → **原样保留** | **77** | 白赚：只要 DOM 上有 `id="write"`，这些规则天然生效 |
| 裸标签选择器（`h1`、`table`、`blockquote`…）→ **映射改名** | **73** | 靠 §5.2 映射表 |
| `@font-face`（含 23 个）→ **保留** | 23 | 字体是 T1 必达项 |
| `@keyframes` 的 `from`/`to`/`50%` → **保留** | 17 | 动画关键词被误判成选择器，解析器要专门跳过 |
| `.cm-s-inner` token 配色 → **剥作用域后保留** | 23 | 原计划丢弃。实测发现丢弃后代码块**一个字都不变色**（高亮器只给了最朴素的几个样式），观感上「根本不像代码块」。改为把 `.cm-s-inner` / `.CodeMirror*` 这些 Typora 的 CodeMirror 5 作用域类剥掉、`.cm-*` 经映射表改写成 CM6 的 `.tok-*`（`classHighlighter`），主题配色原样落地；剥完只剩裸标签的规则（如 `.cm-s-inner.CodeMirror{background}`）仍然丢弃，否则裸 `div` 会命中全页 |
| 应用外壳专属 → **丢弃** | 10 | `#typora-sidebar`、`#typora-quick-open`、`#file-library-search-panel`、`.megamenu-content`、`.typora-export *`… |
| 其余（`span[alt=...]`、`kbd`、`.footnotes`、`.MathJax_SVG_Display`、`video/audio:focus`） | ~20 | 见下表逐一处理 |

> **注**：`@keyframes` 内部的 `from`/`to`/`50%` 会被朴素的"正则抓 `xxx {`"误当成选择器 —— 这是实现时一定会踩的坑，**必须用真正的 CSS 解析器（postcss），不能正则**。

### 5.3.2 那 ~20 条特殊选择器：决定"像不像"的真正细节

| 选择器 | 需要 DOM 提供什么 | 不做的后果 | 你的库 |
| --- | --- | --- | --- |
| `h1 span:after`、`h1:hover span:after` | **标题文字外面要包一层 `<span>`** | 标题下那条悬停展开的横线**完全不出现**（`dyzj` 的招牌效果） | 必做 |
| `blockquote::before` + `font-family:"iconfont"` | 递归内联后的 iconfont `@font-face` 必须能解析 | 引用块左边是**方块乱码**而不是图标 | 必做 |
| `table tr:nth-child(2n)`、`table tr:hover` | 真 `<table><tr>`，且 `:hover` 要能命中 | 斑马纹与悬停高亮失效 | 106 篇有表格 → 必做 |
| `.md-fences:not(.md-focus) .CodeMirror-code>*:hover` | 代码块每一行套 `.jd-code-line` | 代码行悬停高亮失效 | 163 篇有代码块 → 必做 |
| `.md-fences.md-focus .CodeMirror-code>div.CodeMirror-activeline` | 当前代码行要有"激活行"标记 | 光标所在代码行不突出 | 必做 |
| `.md-task-list-item > input` | 真 `<input type="checkbox">` | 复选框变成纯字符 | 1 篇 → 低 |
| `.footnotes` / `kbd` / `.MathJax_SVG_Display` | 脚注 / 快捷键 / 公式容器 | 样式缺失 | 脚注 1 篇、`<kbd>` 0 篇 → 低 |
| `span[alt="blink"]`、`div[alt="timenode"]`、`div[alt="three-table"]` 等 | `alt` 属性当"自定义容器"钩子 | 这些花哨组件不生效 | **实测 0 处使用** → 放弃 |

> **`==高亮==` 这条值得单独说**：`dyzj` 给 `mark` 写了一套很显眼的黄底规则，但实测你的库**真实高亮用法 0 处**（45 处 `==` 命中全是代码或表格里的比较运算符，逐行核对过，见 §1.3）。所以「高亮」对你**可做可不做**，视觉上也不必为它让步。同理 `<details>` / `<video>` / `<kbd>` 全是 0。
> **结论：优先级全部让给代码块和表格** —— 这才是这个库里天天出现的东西。


### 5.4 零拷贝：直接读 Typora 的主题目录 —— 顺带找到你痛的根因

**实测发现的真正原因，比"要多复制一次"更具体：**

```
笔记库   D:\BaiduSyncdisk\笔记        ← 在百度网盘同步范围内 ✅ 多机自动一致
主题     C:\Users\...\AppData\Roaming\Typora\themes  ← 不在任何同步范围 ❌ 每台机器各一份
```

所以你真正在经历的是：**内容同步了，主题没同步**。换机器 / 加机器，笔记都在，但外观回到默认，得手动把 `themes` 目录再搬一次。18 个主题、13 个子目录——搬一次很烦。

**这也意味着一份更便宜的解法**（写在这里供你权衡，我不擅自扩大范围）：

| 方案 | 做法 | 成本 | 效果 |
| --- | --- | --- | --- |
| **X. 把主题目录搬进同步盘**（零代码） | 把 `themes` 移到 `D:\BaiduSyncdisk\` 下，再在原位置建一个目录符号链接 `mklink /D` 指回去 | 5 分钟，永久生效 | **彻底解决"主题不同步"**，Typora 与简牍都受益 |
| **Y. 应用内零拷贝读取**（本项目做法） | 编辑器直接读 `%APPDATA%\Typora\themes`，不做副本 | 已在做 | 解决"编辑器不用重复配主题" |

> **建议 X 和 Y 都做**：X 是十分钟的运维动作，收益立竿见影；Y 是产品能力。**X 不能替代 Y，Y 也不该假装自己是 X 的替代品。**
> 我没擅自去改你的 `themes` 目录——那会影响正在用的 Typora。要做的话说一声，我给你一条命令并验证。

**Y 的实现要点：**

- 启动时扫描主题目录，**不复制、不缓存副本**，只读。
- 好处：Typora 装新主题 → 下拉里立刻出现；`themes` 一旦进了同步盘 → 所有机器自动一致。
- 兜底：目录不存在 → 用内置亮暗两套；`config.ts` 里可手动指定目录。
- **多张 CSS 叠加**：实测 `night/` 下有 `codeblock.dark.css`、`sourcemode.dark.css`、`mermaid.dark.css`。所以主题 = `主 css` + `同名字源目录里的附加 css`，按顺序加载（主 css 在前）。

### 5.5 字体与相对资源：必须重写 URL

**先看一组实测数据，这条为什么是致命的：**

| 字体 | 系统里装了吗 | 结论 |
| --- | --- | --- |
| **Source Sans Pro**（`dyzj` 的正文字体） | ❌ **没装** | 只能靠主题自带的 22 个 woff2（`themes/source/zj/`） |
| **JetBrains Mono**（代码字体） | ❌ **没装** | 只能靠主题自带的 `JetBrainsMono-Regular.woff2` |
| 等距更纱黑体 SC（`dyzj` 的中文回退） | ❌ **没装** | 主题也没带 → 中文回退到系统默认 |
| 微软雅黑 / 宋体 / 黑体 | ✅ 已装 | 系统字体 |

→ **`dyzj-dark.css` 的英文字体 100% 依赖主题自带的 `@font-face`。** 一旦 URL 没重写对，字体 404，英文静默退回 Arial —— 字宽、字形、行高全变，**这就是"看着就是不像"最隐蔽的原因**，而且控制台不一定报错。

字体文件的实际写法（`themes/source/zj/fonts.css`）：

```css
@font-face {
  font-family: 'JetBrains Mono';
  src: url('JetBrainsMono-Regular.woff2') format('woff2');
}
@font-face {
  font-family: 'Source Sans Pro'; font-weight: 400;
  src: url('6xK3dSBYKcSV-LCoeQqfX1RYOo3qOK7l.woff2') format('woff2');
  unicode-range: U+0000-00FF, ...;
}
```

> 注意这是**相对 `fonts.css` 所在目录**（`themes/source/zj/`）的路径，不是相对主 css。所以"每层以自己的目录为基准重写"不是可选项，是正确性的一部分。
> 这些 `@font-face` 都带 `unicode-range`，浏览器按需分片加载 —— **必须原样保留这个字段**，否则会一次拉 22 个文件。

此外还有 **5 个别的主题也带 `@font-face`**（github 4 个、newsprint 4 个、onedark 4 个、pixyll 8 个、keepstyle 1 个，合计 21 个 woff2），写法为 `url("./github/open-sans-v17-latin-regular.woff2")`。

若把 CSS 直接注入 `<style>`，相对 URL 会**相对应用自身的 `file://` 基址解析**，结果 404、字体静默回退——且**不会报错**。这是"主题看着不对"的头号原因。

处理规则：

1. `url()` 里的相对路径 → 改写为 `file:///<主题目录绝对路径>/...`（URI 编码中文与空格）。
2. 图片类 `url()`（png/jpg/gif/svg）同样处理（sneh、chocolate-box、dyzj 均有 `./bg-dark.gif`）。
3. 绝对 `http(s)://` → 保留（但离线环境会挂，报告里标注）。
4. `local("Source Sans Pro")` 类**字体名** → 原样保留（实测这一份主题里 `local()` 出现 42 次，是 `@font-face` 的常见写法，不是路径，不能碰）。
5. **`url()` 里的查询串必须剥掉**：实测 `iconfont.min.css` 写的是 `url('iconfont.woff2?t=1670129411561')` —— 这是给浏览器做缓存击穿的，`file://` 下带 `?t=` 会**直接 404**。重写时拆成"路径 + 查询串"，路径转 `file://`，查询串丢弃。
6. `url(data:...)` 内联资源 → **原样保留**（实测有 1 处），不要去解析或转码。
7. 改写失败或文件不存在 → **在兼容报告里显式列出**，不静默吞掉。

> 这一节的三条（5、6、7）都是"不实测就一定会踩"的类型：`?t=` 和 `data:` 的 bug 现象都是"字体/图标静默失效，控制台干净"。**静默失效是主题兼容最大的敌人**——所以第 7 条"路径解析不到就报错"比"尽量兜底"更重要。

### 5.6 保真度分级 + 可度量

不追求 100%，但必须**知道我差在哪**，所以内置一个"主题兼容报告"面板（开发模式 `F12` 可看）。

| 等级 | 内容 | 目标 |
| --- | --- | --- |

**由此得到三条硬约束：**

1. **落盘约定完全复刻**：`./.${笔记名}.assets/`，文件名沿用 Typora 风格（`image-<时间戳>-<毫秒>-<序号>.png`）。理由：用别的规则（比如统一 `assets/YYYY/MM/`）会让同一个库里两套图片目录并存，以后想退回 Typora 或换工具时更乱。**这一条推翻了我 v0.2 的"统一落 `assets/YYYY/MM/`"设计。**
2. **必须兼容反斜杠路径**：库里有 62 处写成 `.错题集.assets\image-xxx.png`（Windows 风格）。浏览器 `<img src>` 里的 `\` **不会被当作路径分隔符**，直接给浏览器就 404。所以**加载前统一把 `\` 归一成 `/`**（只在渲染层归一，**不回写文本**——否则就是破坏无损原则）。

   - ❌ 静默用空白顶掉（用户永远不知道少了图）
   - ❌ 渲染成花哨的"图片加载失败"卡片（这就不像 Typora 了）
   
   Typora 自己显示的是 `<img>` 的 alt 文本/破图标。**保持平庸，但把路径露出来**，是这个库里最实用的选择：作者一眼能看到"哦这张图当年没同步过来"。

### 5.8 无损原则（唯一不能妥协的）

> 任意 `.md` → 打开 → 不改 → 保存 → 内容语义不变。

- 纯文本是唯一真源；渲染层只读叠加，**永不回写"美化后"的文本**。
- 不认识的语法（HTML 块、奇怪表格、自定义容器）→ 原样保留，渲染成等宽文本，绝不改写。
- **保留 CRLF/LF 原样**（实测你的库混用：`职业4级.md` 是 CRLF，`UE知识体系完整手册.md` 是 LF）。不统一、不转换。
- 保留 BOM、末尾空行、列表缩进风格。
- **保留图片路径的原样写法**：62 处反斜杠路径只在渲染时归一成 `/`，**文本里还是 `\`**。不自作主张"修正"路径。
- 自测：`fixtures/` 直接指向库里 30 篇真实笔记，跑 `打开→保存→逐字节比对` 必须完全相同（**注意：库里没有 git，见下**）。
- **隐藏目录不入树**：`.obsidian/`、`.pandoc-3.6.4/`、`.workbuddy/`、`.主题/`、`.???.assets/` 不显示为笔记，也不参与任何扫描统计。

**这把"无损"落到可执行的验收脚本上**（M1 就要有）：

```
scripts/verify-roundtrip.mjs
  1. 遍历库里全部 245 篇 .md
  2. 逐篇：读原文 → 编辑器 load → 不改 → save → 读回
  3. 断言：读回的字节 === 原文的字节（不是"语义相等"，是逐字节相等）
  4. 输出：通过/失败清单 + 图片裂图数（基线 94，不能变大）
```

> 用**逐字节相等**而不是"语义相等"，是因为后者永远说不清。CRLF、BOM、末尾换行、列表缩进——全都藏在这一个断言里。

## 附录 C · 主题选择器映射表

> **不抄表。** 唯一真相源是 `src/theme/mapping.json`：开发期可热改（`loadMapping` 优先读磁盘那份），
> 构建期由 rollup 内联成 `DEFAULT_MAPPING` 作兜底 —— **两份同源，不存在漂移的可能**。
> 打包后在 `resources/theme/mapping.json`。
>
> 这份附录曾经抄过一份，已经漂移，而且漂成了最坏的那种：
>
> | 抄错的 | 真源 | 后果 |
> | --- | --- | --- |
> | `"th": "jd-table-cell"`（与 `td` 共用） | `jd-table-head-cell` | 主题的 `table tr th{background}` 命中所有单元格 → **整表变绿** |
> | `classes` 只到 `md-tag` | 另有 19 条 `.cm-*` → `.tok-*` | 代码块有底色、有边框，但一个字都不变色 |
>
> 这两条正好是 README「已知的坑」里记过的同一个错误 —— 代码那边守住了，文档这边忘了。

三条约定（值**不带**前导点：翻译器走 `postcss-selector-parser` 的 `className({value})`
换节点，写 `.jd-h1` 会变成 `..jd-h1`）：

| 分组 | 作用 | 例 |
| --- | --- | --- |
| `tags` | 裸标签换成语义类 | `h1` → `jd-h1` |
| `classes` | Typora 类名改名 | `md-fences` → `jd-code-block` |
| `ids` | id 名改名 | `typora-source` → `jd-source` |

`classes` 里那 19 条 `.cm-*` → `.tok-*` 是代码高亮的关键：主题写的是 CodeMirror **5** 的
token 类，我们的 DOM 没有 `.cm-s-inner`，照搬过来永远不命中。`theme.ts` 的
`stripCodeMirrorScope()` 剥掉作用域后，靠这份表改名成 CM6 `classHighlighter` 产出的
`.tok-*`，主题自带的高亮配色才真正落地。

**整条规则丢弃**的黑名单不在这里，在 `src/main/theme.ts` 的 `SHELL_BLOCKLIST`（代码里写），
因为那些选择器指向 Typora 应用外壳，属于「没有对应 DOM 就整条扔掉」的判断，
不是「改个名字」。

**实跑结果（`dyzj-dark.css`，2026-10-27）**：内联 5 个文件（4 层 `@import`）→ 应用 **262** 条、丢弃 **13** 条、`@font-face` **23** 个、`@keyframes` **11**、`:root` 变量 **58**、URL 重写 **24** 处、警告 **4** 条。

> `content` 那条是实测必需项（见 §5.2-E）：去掉它 `dyzj-dark` 的右下角背景图和页面底色直接消失。
> `code` 与 `kbd` 是**实现期才发现的必需项**：CM6 不生成 `<code>` 元素，`#write code{padding:2px 4px; background:var(--codebg-color)}` 永远匹配不到，行内代码就没有底色。现在由 `markers.ts` 给行内代码内容挂 `.jd-code-inline`。
> 没有 `pre.jd-code` / `.jd-code-inner` 这类当初设想的"块级代码容器"：CM6 一行一个 `.cm-line`，代码块是**一串** `.jd-code-block` 行，靠 `theme-fix.css` 的 `:not(.jd-code-first)` / `:not(.jd-code-last)` 拼回一个框。

### C.1 翻译期的三个必要修正（都不是主题的错，是 CM6 的模型差异）

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| `####` 的虚线框横跨整行 | 主题写 `h4{display:inline-block}`，但 CM6 强制 `.cm-line{display:block}` | 翻译时改成 `display:block` + `width:fit-content`（**正则只认 `.jd-h1..6` 本体，不认 `::before`**——认了会把 h2 的风车图标撑成整块） |
| `url(iconfont.woff2?t=1670129411561)` 字体不生效 | `file://` 下带查询串直接 404 | 拆成路径+查询串，路径转 `file://`，**查询串丢弃**并记警告 |
| `@import` 只读一层等于没装主题 | `dyzj-dark.css` 本体只有 60 行，规则全在 `source/` 里 | 递归内联到底（上限 8 层 + 环形检测），每个文件的 `url()` 以**它自己所在目录**为基准 |

**不修正的**：`--bgimg-url: url(./bg-dark.gif)` 指向的 `themes/bg-dark.gif` 根本不存在（真图在 `themes/source/bg-dark.gif`）。这是主题自己的 bug，**Typora 里也不显示**。目标是"和 Typora 一样"，不是"比它好看"——原样复刻。
